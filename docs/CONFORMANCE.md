# Conformance statement — `ansi-nist-itl`

Status: statement for the `develop` branch after 1.0.2, written on 2026-11-18.
Each claim names the code or the test that supports it. What could not be
checked is marked **not verified**.

## 1. Scope

| Item | Statement | Evidence |
|------|-----------|----------|
| Standard of the tables | ANSI/NIST-ITL 1-2011 Update 2015 (NIST SP 500-290e3), Tables 34 to 126 | `src/dictionary/update2015.rs` (generated by `tools/standard/gen_dictionary.py`) |
| Versions validated against these tables | 1.002 = `0500`, `0501`, `0502` | `Standard::for_version`, `src/dictionary/mod.rs` |
| Versions read and written, without tables | Any 1.002, in particular `0200`, `0300`, `0400` (and `0201` in the public files of §6) | `tests/versions.rs`; §6 |
| Encoding | Traditional encoding only (tagged and binary records, separators FS, GS, RS, US) | `src/message/` |
| Not supported | XML / NIEM encoding (PRD LIB-22); editions after Update 2015, including ANSI/NIST-ITL 1-2025 | `docs/PRD.md` §4.2, §9 |
| Compatibility baseline | Same parsing, errors, `to_bytes` output and summary as `nistitl` 0.6 (IDEMIA) | `tests/oracle.rs`, `tests/reference_doctests.rs`, `tests/reference_edge_cases.rs` |

The parser never reads 1.002: every version is read and written the same way,
and no rule of the parser depends on the version (crate documentation,
"Versions"; `tests/versions.rs::no_rule_per_version`). Only the validation
looks at 1.002.

Version `0500` (1-2011) and `0501` (Update 2013) files are validated with the
Update 2015 tables. Where the editions differ, a file correct for its own
edition can get a finding; see §5.

## 2. Record types

Columns:

- **Read**: `Message::parse` (strict mode, the behaviour of `nistitl`).
- **Tolerant**: `Message::parse_with(.., ParseOptions::tolerant())`.
- **Write**: `Message::to_bytes` (recomputes LEN and CNT, sorts fields as `nistitl` does).
- **Exact**: `Message::to_bytes_exact` gives back the bytes read.
- **Validated**: what `Message::validate` checks for the record.

| Type | Kind | Read | Tolerant | Write | Exact | Validated |
|------|------|------|----------|-------|-------|-----------|
| 1 | tagged | yes | yes | yes | yes | dictionary + 7-bit ASCII (section 5.6) + CNT (1.003) |
| 2 | tagged | yes | yes | yes | yes | dictionary (user-defined content not checked) |
| 3, 5, 6 | binary | yes, with a deprecation warning | yes | yes | yes | deprecation warning only |
| 4, 7, 8 | binary | yes | yes | yes | yes | record type only; header values not checked |
| 9 to 22 | tagged | yes | yes | yes | yes | dictionary |
| 98, 99 | tagged | yes | yes | yes | yes | dictionary |
| 23 to 97 | — | refused (as `nistitl`) | read, with an `UnknownRecordType` diagnostic | refused | — | error `RecordType` |

Evidence: `tests/conformance.rs::every_record_type` builds a version `0502`
message for each type 2 to 99, then checks the strict and tolerant reading, the
exact writing and the validation; `undefined_record_type` checks a Type-50.
Binary records: only LEN and IDC are read, the rest is the raw value, as in
`nistitl` (`src/record/binary.rs`); the image header is decoded on request
(`BinaryRecord::image_header`, Types 3 to 6; `signature_header`, Type-8).

### Validation levels

| Level | Checked | Rule (`validation::Rule`) |
|-------|---------|---------------------------|
| Structure | Record type defined by the edition; field number defined, reserved or deprecated; single value against subfields and items; number of subfields; number of items | `RecordType`, `UndefinedField`, `ReservedField`, `DeprecatedField`, `Structure`, `SubfieldCount`, `ItemCount` |
| Dictionary | Mandatory fields and items, character type, size, dates (`YYYYMMDD`, `YYYYMMDDhhmmss`, GMT) | `MissingField`, `MissingItem`, `CharacterType`, `Size`, `Date` |
| Message | Type-1 in 7-bit ASCII; CNT lists the records of the message | `Type1Ascii`, `Content` |
| Conditional rules | **Not checked**: the dependent conditions (`D`) of the tables, except that Type-9 field blocks are mandatory only when used | `src/validation/mod.rs` module documentation; `block_in_use` |
| Value constraints | **Not checked**: value ranges and code lists of the tables | idem |

Sizes are counted in bytes, since the crate reads text one byte per character
(`src/validation/mod.rs`). Special characters of `ANS`, `AS` and `NS` accept
any printable ASCII character (`allowed`). Versions without tables get a
`Version` warning and only the CNT check.

Evidence: `tests/validation.rs`, `tests/dictionary.rs`, unit tests in
`src/validation/mod.rs`.

## 3. Character encodings (1.015)

## 5. Known deviations and limits

1. **Repeated items are reported as errors.** The validator matches the items of a subfield one to one with the item definitions and ignores how many times an item may occur. Point lists (10.015, 10.033, 10.045, 14.025, 17.033 to 17.037, 9.300 ROI polygon) and the user-defined items of 18.018 get false `ItemCount` and `MissingItem` findings; the format check of the items after the first repeated one uses the wrong definition. Issue [#97](https://github.com/ybdn/ansi-nist-itl/issues/97).
2. **10.011 CGA is typed `A`** (3 to 5 characters) in the dictionary, which refuses `JP2` and `JP2L`, compression codes of Table 15; the CGA of the other image types is `AN`. Whether SP 500-290e3 says `A` for Type-10: **not verified**. Not filed yet (see the pull request of this document).
3. **Versions `0500` and `0501` use the Update 2015 tables.** On the public files of §6, 21.005 (`ACD`, a date in a `0500` file, a date and time in the 2015 table) and item sizes of 10.049, 11.012, 11.035, 11.037 and 12.011 (`0501` files) are reported. Whether these are edition differences or defects: **not verified**.
4. **Field numbers above 999.** BioCTS gives `pass-type-1-long-fieldnumber.an2` (field 2.999999999) as conformant; the validation reports `UndefinedField`. Whether the 2015 tables allow it: **not verified**.
5. **Fields after the data field (999)** are read as part of the data, as `nistitl` does (quirk E5); the tolerant mode reports a `DataNotLast` warning (`src/error.rs`). Five NBIS files of §6 have this layout.
6. **Binary records (Types 3 to 8)**: header values (IMP, FGP, ISR, HLL, VLL, GCA) are not validated (§2).
7. **Not checked**: dependent conditions, value ranges and code lists, content of user-defined fields (§2).
8. **Not supported**: XML/NIEM, Annex B.1.8 switch sequences, editions after Update 2015.
9. **Portability**: CI runs on Linux; Windows has a manual job; macOS is not tested in CI (PRD QA-06).

# Corpus: a directory of the extracted .an2 files, outside the repository.

`corpus_report` prints one line per file and the totals, and fails if a file
the strict mode accepts is not written back exactly.

## 7. BioCTS on files written by the crate — not run

BioCTS for ANSI/NIST-ITL is a Windows application of NIST that tests
transactions against the test assertions of the conformance testing
methodology (NIST SP 500-295, levels 1 and 2). It has not been run on files
written by the crate. Procedure:

1. Write test files with the crate, for instance the synthetic seed corpus: `cargo run --example fuzz_seeds -- /path/out`, or a program that builds `0502` messages with `Message::to_bytes`.
2. On Windows, install BioCTS for ANSI/NIST-ITL from the page of §6.
3. Load each file in traditional encoding, run the level 1 and level 2 assertions, export the report.
4. Record here: BioCTS version, number of files, SHA-256 of the list, assertions failed and their cause.
