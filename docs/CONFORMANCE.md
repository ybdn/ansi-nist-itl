# Conformance statement — `ansi-nist-itl`

Status: statement for the `develop` branch after 1.0.2, written on 2026-11-18.
Each claim names the code or the test that supports it. What could not be
checked is marked **not verified**.

## 1. Scope

| Item | Statement | Evidence |
|------|-----------|----------|
| Standard of the tables | ANSI/NIST-ITL 1-2011 Update 2015 (NIST SP 500-290e3), Tables 34 to 126 | `src/dictionary/update2015.rs` (generated by `tools/standard/gen_dictionary.py`) |
| Versions validated against these tables | 1.002 = `0500`, `0501`, `0502` | `Standard::for_version`, `src/dictionary/mod.rs` |
| Versions read and written, without tables | Any 1.002, in particular `0200`, `0300`, `0400` (and `0201` in the public files of §6) | `tests/versions.rs`; §6 |
| Encoding | Traditional encoding only (tagged and binary records, separators FS, GS, RS, US) | `src/message/` |
| Not supported | XML / NIEM encoding (PRD LIB-22); editions after Update 2015, including ANSI/NIST-ITL 1-2025 | `docs/PRD.md` §4.2, §9 |

The parser never reads 1.002: every version is read and written the same way,
and no rule of the parser depends on the version (crate documentation,
"Versions"; `tests/versions.rs::no_rule_per_version`). Only the validation
looks at 1.002.

Version `0500` (1-2011) and `0501` (Update 2013) files are validated with the
Update 2015 tables. Where the editions differ, a file correct for its own
edition can get a finding; see §5.

## 2. Record types

Columns:

- **Read**: `Message::parse` (strict mode: the first error stops the reading).
- **Tolerant**: `Message::parse_with(.., ParseOptions::tolerant())`.
- **Write**: `Message::to_bytes` (recomputes LEN and CNT, writes fields in tag order).
- **Exact**: `Message::to_bytes_exact` gives back the bytes read.
- **Validated**: what `Message::validate` checks for the record.

| Type | Kind | Read | Tolerant | Write | Exact | Validated |
|------|------|------|----------|-------|-------|-----------|
| 1 | tagged | yes | yes | yes | yes | dictionary + 7-bit ASCII (section 5.6) + CNT (1.003) |
| 2 | tagged | yes | yes | yes | yes | dictionary (user-defined content not checked) |
| 3, 5, 6 | binary | yes, with a deprecation warning | yes | yes | yes | deprecation warning only |
| 4, 7, 8 | binary | yes | yes | yes | yes | record type only; header values not checked |
| 9 to 22 | tagged | yes | yes | yes | yes | dictionary |
| 98, 99 | tagged | yes | yes | yes | yes | dictionary |
| 23 to 97 | — | refused | read, with an `UnknownRecordType` diagnostic | refused | — | error `RecordType` |

Evidence: `tests/conformance.rs::every_record_type` builds a version `0502`
message for each type 2 to 99, then checks the strict and tolerant reading, the
exact writing and the validation; `undefined_record_type` checks a Type-50.
Binary records: only LEN and IDC are read, the rest is the raw value
(`src/record/binary.rs`); the image header is decoded on request
(`BinaryRecord::image_header`, Types 3 to 6; `signature_header`, Type-8).

### Validation levels

| Level | Checked | Rule (`validation::Rule`) |
|-------|---------|---------------------------|
| Structure | Record type defined by the edition; field number defined, reserved or deprecated; single value against subfields and items; number of subfields; number of items; repeated items: HPO and VPO pairs after NOP (section 7.7.12.2), Type-9 EFS paths `x,y-x,y` in one item, each vertex two non-negative integers, at least 3 vertices for the closed paths and 2 for 9.373 RPS, at most 99 (sections 7.7.12 and 7.7.12.1), lists `a\|b` in one item (section 7.7.13) | `RecordType`, `UndefinedField`, `ReservedField`, `DeprecatedField`, `Structure`, `SubfieldCount`, `ItemCount` |
| Dictionary | Mandatory fields and items, character type, size, dates (`YYYYMMDD`, `YYYYMMDDhhmmss`, GMT) | `MissingField`, `MissingItem`, `CharacterType`, `Size`, `Date` |
| Message | Type-1 in 7-bit ASCII; CNT lists the records of the message | `Type1Ascii`, `Content` |
| Conditional rules | **Not checked**: the dependent conditions (`D`) of the tables, except that Type-9 field blocks are mandatory only when used, and that NOP and the HPO VPO pairs are absent together or NOP gives their number | `src/validation/mod.rs` module documentation; `block_in_use` |
| Value constraints | **Not checked**: value ranges and code lists of the tables | idem |

Sizes are counted in bytes, since the crate reads text one byte per character
(`src/validation/mod.rs`). Special characters of `ANS`, `AS` and `NS` accept
any printable ASCII character (`allowed`). Versions without tables get a
`Version` warning and only the CNT check.

Evidence: `tests/validation.rs` (`points_repeat_as_pairs`, `efs_path_in_one_item`,
`efs_open_path`, `lists_in_one_item`, `user_defined_items_are_free_but_present`,
`face_compression_jpeg_2000` among others), `tests/dictionary.rs`, unit tests in
`src/validation/mod.rs`. User-defined items (18.018: "there may be multiple items")
may be any number with any content, but each must be present.

The minimum number of points is the one of each table, which can differ from
section 7.7.12: 10.033 FEC is an open path, for which the text asks at least 2
vertices, but its table gives NOP at least 3; the crate follows the table.

## 5. Known deviations and limits

1. **Fixed: repeated items were reported as errors** (issue [#97](https://github.com/ybdn/ansi-nist-itl/issues/97)). The validator matched the items of a subfield one to one with the item definitions. It now follows sections 7.7.12 and 7.7.13 (§2), 9.373 RPS included; the user-defined items of 18.018 are free in number and content.
2. **Fixed: 10.011 CGA was typed `A`.** The Type-10 table of SP 500-290e3 does say `A` (note 150: "Earlier versions had AN"), but note 151 takes the value from Table 19 except `WSQ20`, and Table 19 holds `JP2` and `JP2L`. Annex E.6.1.2 also requires JPEG 2000 for facial images at SAP levels 40 and above. The dictionary now gives `AN`, as for the other image types (`tools/standard/gen_dictionary.py`, `TYPE_FIXES`): a deviation from the letter of the table, in favour of Table 19. Consequence: since the crate does not check code lists (item 7), `WSQ20`, the value note 150 meant to exclude, is now accepted in 10.011.
3. **Versions `0500` and `0501` use the Update 2015 tables.** On the public files of §6, 21.005 (`ACD`, a date in a `0500` file, a date and time in the 2015 table) is reported. Whether this is an edition difference or a defect: **not verified**. (The findings on 10.049, 11.012, 11.035, 11.037 and 12.011 that this item listed before came from item 1: they were lists of section 7.7.13.)
4. **Field numbers above 999.** BioCTS gives `pass-type-1-long-fieldnumber.an2` (field 2.999999999) as conformant; the validation reports `UndefinedField`. Whether the 2015 tables allow it: **not verified**.
5. **Fields after the data field (999)** are read as part of the data; the tolerant mode reports a `DataNotLast` warning (`src/error.rs`). Five NBIS files of §6 have this layout.
6. **Binary records (Types 3 to 8)**: header values (IMP, FGP, ISR, HLL, VLL, GCA) are not validated (§2).
7. **Not checked**: dependent conditions, value ranges and code lists, content of user-defined fields (§2), and that two vertices of a path differ (section 7.7.12).
8. **Not supported**: XML/NIEM, Annex B.1.8 switch sequences, editions after Update 2015.
9. **Portability**: CI runs on Linux and macOS (`test-macos`); Windows has a manual job (`.github/workflows/ci.yml`).
10. **Tag format width at most 1024** (`MAX_WIDTH`, `src/py/format.rs`): a `%[0][width]d` conversion wider than that, accepted before up to about 10^8 characters, is refused with `ErrorKind::BadFormat`.
11. **Items nested at most 128 levels deep** (`MAX_ITEM_DEPTH`): a deeper list of items, given through the API or a deserialized form, is refused with `BAD_SUBFIELD_VALUE` instead of overflowing the stack. A file never nests items.

## 7. BioCTS on files written by the crate — not run

BioCTS for ANSI/NIST-ITL is a Windows application of NIST that tests
transactions against the test assertions of the conformance testing
methodology (NIST SP 500-295, levels 1 and 2). It has not been run on files
written by the crate. Procedure:

1. Write test files with the crate, for instance the synthetic seed corpus: `cargo run --example fuzz_seeds -- /path/out`, or a program that builds `0502` messages with `Message::to_bytes`.
2. On Windows, install BioCTS for ANSI/NIST-ITL from the page of §6.
3. Load each file in traditional encoding, run the level 1 and level 2 assertions, export the report.
4. Record here: BioCTS version, number of files, SHA-256 of the list, assertions failed and their cause.
